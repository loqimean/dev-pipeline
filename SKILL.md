# Dev pipeline

One process for every change: requirements, architect plan, engineer, architect review, fixes until approved, tests, evidence report.
Roles stay separate. The architect runs on the most capable model, the engineer on a cheaper one, and the orchestrator only coordinates.

Diagram and rationale: [README.md](README.md). Prompt templates are in `templates/`, helper scripts in `scripts/`.
Local setup (which tools and models fill each role, commit identity) lives in `config.local.md` next to this file. It's git-ignored; copy [config.example.md](config.example.md) to create it.

## Roles

- **Owner:** the person the work is for. Approves big or risky plans, merges, approves deploys.
- **Orchestrator:** the agent session talking to the owner. Owns the ledger, writes dispatch briefs, routes findings, reports. Never writes product code and never fixes review findings itself (that skips review). An owner's "yes, implement X" in the middle of a session is a dispatch, not a license to code it directly; if you already did, tell the owner those commits are unreviewed and put them in the next architect review's scope. One exception, only with the owner's yes: after the round cap, a handful of mechanical leftovers (comment wording, moving setup into hooks, a gate regex) can be fixed by the orchestrator, then `bin/ci` + a scoped architect check of that commit like any fix round. When the owner says to skip the workflow ("don't use the dev workflow for now", usually for quick visual polish), stop any running lane on that branch and make the change yourself: edit, run the touched tests then the full suite and lint, re-shoot the screenshots and look at them, commit with the project's author, push, replace the PR body images, and show him the shots in chat. No architect review unless he asks. While that ban stands, a big new feature (hours of work) still shouldn't be built inline in the chat turn: dispatch ONE background `delegate_task` subagent with a role and a self-contained brief (worktree and test/e2e commands, hard limits, commit author and copy rules, the exact build list, which records must be isolated or covered by tests, the evidence list with viewport sizes and a short H.264 video, "look at your own screenshots and fix what's ugly", finish = push + PR with evidence attached, return SHA, raw counts, evidence paths, migration plan, known gaps, no merge or deploy). Ack the owner in one message and end the turn. Answer "status?" from the branch's `git log`, `delegate_task(action='list')` and the transcript tail on the Hermes host (`ssh` to it; the path isn't on the terminal host). When it returns, verify before reporting: full suite on a fresh worktree of the pushed head, the migration on a prod-data snapshot, the body's attachment count, and your own look at the shots.
- **Architect:** the most capable model, run as a separate read-only session. Writes the plan, reviews diffs. May write only the plan file.
- **Engineer:** a cheaper model in its own session with the project's context. Implements, tests, commits, pushes. Never spawns its own reviewer.

## Stages

### 1. Requirements

- Restate the ask in one short list: scope, out of scope, constraints from the project's notes.
- **Where does it live?** When the owner names a new product concept ("a Factory", "a hub for X") that overlaps a flow the product already has, it usually means extending that flow, not a new section. Default to extending the existing flow (extra options behind an "Advanced" toggle) and say so in the plan summary; if you'd rather build a separate area, ask first. A wrong guess here gets discovered only after whole phases are built and has to be re-planned.
- Ask the owner only what blocks the plan. One message, max 3 questions, recommended option first.
- Write the spec to `docs/plans/<date>-<slug>.md` in the worktree (or a scratch folder). The spec is the binding authority for every later stage.
- The owner points at a design file ("implement frame X", "we updated the design"): read it as data and hand the engineer exact frame values. Recipe in [references/design-files.md](references/design-files.md).
- The owner says "like this" but no attachment arrived: check the inbound media cache by modification time (newest file vs the message time) before anything else, then ask him to resend. If he answers the other questions without resending, build from the product's existing design and say in the report that the example never arrived, so he can redirect.

### 2. Architect plan

- Dispatch with [templates/architect-plan.md](templates/architect-plan.md). The architect reads the spec and the code, not the chat.
- The plan lists tasks, each with files, exact values, a verification command, and a `risky: yes|no` flag.
- **New codebase or big rewrite: the plan starts with a "Target architecture" section** (directory tree, one line per file, which layer owns what) and, for a rewrite, a move map (every current file → its new home, what gets deleted). Owners read the code; a working-but-flat first version (logic in `lib/` files, SQL strings in controllers) gets sent back as messy, and refactoring after the fact costs a second full pass.
- **Owner changes direction mid-run** (new structure, new library, "I meant X, not a separate Y"): if the running engineer's work overlaps the change, stop it early (kill every driver and engineer PID, confirm 0), push unpushed sibling branches so nothing is lost, keep what's reusable (services, spike branches, reports), and have the architect re-plan into the SAME branch and PR with a move map (what is kept and re-homed, what is deleted). Don't close the open PR or start a fresh one unless he asks: repurpose it, post a short comment that earlier reviews covered the old scope, and have the engineer rewrite its title, body and Evidence. Don't let it finish work that the next PR rewrites.
- **Approval gate:** send the plan summary to the owner and wait ONLY when the change is big or risky: auth, payments, personal data, DB migrations, deletes, infra, anything irreversible, or more than ~600 changed lines. Otherwise continue and mention the plan in the report. When the owner has already said "do it end to end by morning", that is the go-ahead for the plan: don't stop to ask, list the plan's open questions in the morning report instead.
- **Unattended end-to-end runs ("have it working by morning"):**
  1. Write one binding `context.md` with every owner decision, hard limits of the target host, repo rules and the definition of done, and point the architect at it instead of the chat.
  2. Before dispatching, do the setup engineers can't: create the repo, check credentials' actual permissions (read-only tokens are common), create DNS or tell the owner the exact record to add.
  3. Ask the architect for a spec AND a plan split into independent tracks that depend only on the spec's contract (e.g. service + front end), so the tracks run in parallel.
  4. Anything learned after the architect started goes into an "UPDATE" section of `context.md` and, explicitly, into each engineer brief: a running architect won't re-read the file.
  4a. A track that finishes before the one it depends on runs its end-to-end check against a local mock of the contract. Re-run that check against the real dependency once it's live, before the morning report, and say which backend each result came from. The mock is written from the spec's examples, so it hides the real serializer's shapes (a date the spec shows as `YYYY-MM-DD` came back as a timestamp and crashed an admin panel only against the real service). When the real run finds such drift, fix the consumer to accept both shapes AND send the producer a fix to match the spec.
  4b. When a review of one track finds a trust-boundary bug (e.g. a client forwarding unvalidated IDs to the other track's admin API), add the server-side counterpart (the service rejecting bad IDs itself) to the other track's review focus, so the fix exists on both sides.
  5. Keep the morning report to: what's live and how it was proved, verdict history, the exact owner steps left (numbered), and secrets' locations (files, never values).

- **One feature, run unattended after the owner answered the questions:** write the binding spec to `$D/spec.md`, create the worktree and install deps yourself, then launch [scripts/plan-build-review.sh](scripts/plan-build-review.sh) detached (plan → engineer → review → fix rounds, verdicts posted). Add the watcher job below and end the turn with what runs, where progress is logged, and that nothing gets merged or deployed.
  - Launch it from Hermes as `terminal(background=true, notify=true, persist_on_release=true)` running `cd <run dir> && source env.sh && bash plan-build-review.sh > driver.out 2>&1 < /dev/null`, with the env vars (D, WT, B, GH_REPO, models, PR_TITLE, FOCUS, READ_FILES) in an `env.sh` written beforehand: the terminal tool refuses `nohup`/`setsid` wrappers, and without `persist_on_release` the run dies with the session.
  - `claude -p` roles can't load Hermes skills. Copy whatever project skill depth the engineer needs (e2e recipe with its own port pair, hard limits such as "never touch the prod container") into `$D/<topic>.md` and name that file in the engineer prompt, or the run improvises ports and touches shared services.
  - Put the project's binding rules (copy rules, commit author, no force-push) into `RULES` in
    `env.sh`: the driver appends it to every role prompt, and `claude -p` roles see nothing else.
  - A run that stopped midway (`gave up` after the usage-limit retries, `NO PR` with local commits,
    `fix N: no new commits`) is resumed, not relaunched: [scripts/resume-pipeline.sh](scripts/resume-pipeline.sh)
    with `MODE=engineer RESUME_NOTE="<local commits, uncommitted files, what's left>"` or
    `MODE=fix FROM_REVIEW=<N>`, same `env.sh`, launched the same way. Relaunching the full driver
    re-plans and discards the engineer's unpushed commits' context.
  - A usage limit makes the driver sleep in 20-minute steps (`status.log`: `usage limit ... waiting`;
    the raw log names the reset time). Keep `MAX_TRIES` high (default 12): a subscription session
    limit can take hours to reset, and 4 tries gave up overnight with work half done. Once the reset time has passed, or the owner says "try again",
    don't wait out the sleep: smoke-test the role's model (`claude -p "say ok" --model <id> --max-turns 1`),
    stop the driver with the bracket pattern (`pkill -f "[p]lan-build-review.sh"`, confirm 0), delete the
    empty `plan-raw.md`, append a `relaunched` line to `status.log`, and launch it again the same way.
    Its old background handle then reports exit -1: expected, check the new run is alive.
  - Parallel lanes (a second fix while a feature runs) get their own worktree, run dir with `env.sh`,
    and `$D`; extend the existing watcher job's prompt to cover both instead of a second job. Tell the
    owner they share the CLI quota, so a limit pauses both. Lanes in parallel drain a subscription
    session limit together and then all sleep until the reset; queue non-urgent stages (e.g. a
    review of a third PR) behind a running lane with a background `while kill -0 <driver pid>; do
    sleep 60; done; <launch>` instead of starting them at once.
  - Copy the driver and resume scripts from this skill's `scripts/` (write them onto the remote with
    `write_file`) for every new lane, never from an older run dir: old copies carry a 4-try limit and
    no verdict guard, so they give up overnight and post usage-limit text as a review.
  - Before launching, list `pgrep -f "claude -p"` with each PID's cwd (`lsof -a -p <pid> -d cwd -Fn`): only runs whose cwd is this worktree are conflicts; other repos' runs (notes vaults, other lanes) are fine.
- **One product in several dependent phases ("write all phases and implement them end to end"):** the owner's go-ahead covers every phase's plan, so don't stop between phases.
  1. Before writing specs, map what already exists across every repo the flow touches (`git grep` main, sibling apps' services and routes, Hermes webhook subscriptions): an "integration" phase is often mostly wiring (e.g. an existing endpoint keyed by project/topic/format can attach the result to a pre-created record, so the other app needs no change).
  2. Write one binding `context.md` (owner's flow in his words translated, what exists to reuse, product decisions you made, phases, repo rules, hard limits) plus one short `spec.md` per phase that narrows it. List your own product decisions in the launch message so he can redirect.
  3. Stack the phases: phase n branches from phase n-1's branch and opens its PR against it (`PR_BASE`/`BASE_REF` = previous branch), so each review sees only its own diff. By default run them sequentially with [scripts/phase-chain.sh](scripts/phase-chain.sh) (one `env.sh` per phase with its own port pair). When the owner asks for parallel: phases that depend only on phase 1 (not on each other) start at once from phase 1's current commit, even unpushed (worktrees share refs: `git worktree add -B <b> <wt> <sha>`, `BASE_REF=<sha>`); their `RULES` name what the sibling lane owns, keep shared views additive, and say "before opening the PR, plain-merge the upstream branch if it exists, else open against main with the merge order in the body". A phase that needs two parallel phases waits in a loop for both `DONE ... Approve`, then branches from one and plain-merges the other (stop on conflict). Tell the owner parallel lanes drain the shared quota faster.
  4. Right before launching, re-check the state of any PR a phase branches from (`gh pr view <N> --json state`): if it merged meanwhile, cut from `origin/main` and fix the spec's base and merge-order lines.
  5. One watcher job covers the whole chain (`chain.log` + each phase's `status.log` + PR per branch).
- **A batch of independent features ("build N features, one per hour"):** run them through [scripts/feature-driver.sh](scripts/feature-driver.sh) instead of hand-dispatching each.
  1. Before proposing features, list open PRs and branches (`gh pr list --state open`) and `git grep` main for the idea's key words: half the obvious ideas are often already in an open PR. Back each pick with search evidence of the pain (queries, articles) in its brief.
  2. Write one shared binding `context.md` plus one `BRIEF.md` per feature (pain + evidence links, exact UI copy, flag key, migration name, own port pair, screenshot list, definition of done). Keep state-service links out of briefs too: engineers copy brief links into PR bodies and copy.
  3. Launch the driver detached and create ONE recurring report job (cron with continuity) that reads `status.log`, checks PR state and the last comment, and posts only changes; then end the turn. Update that same job's prompt when a new batch starts instead of creating a second job.
  4. Pacing "N per hour" means sequential, each start at least the slot after the previous start; a feature that finishes early just waits. Parallel lanes (when the owner wants speed) share ports and the base worktree of the check script: serialize the check with a lock dir.
  5. Before telling the owner the batch is ready, verify independently even when every verdict is Approve: run the same tests on main to separate pre-existing failures, compare bundle/size deltas per PR, and list files touched by more than one PR of the batch (sibling PRs editing the same component conflict after the first merge: propose a merge order and who resolves).

### 3. Engineer

- One worktree per feature, branch off the main branch. Never work on main directly.
- Dispatch with [templates/engineer-brief.md](templates/engineer-brief.md): the plan path, the global constraints, the report-file path. No chat history, no prior-task summaries.
- **Before every dispatch, `ls -la <worktree>/.pipeline/` and confirm each file the brief names exists.** `.pipeline/` is git-ignored, so a fresh worktree has none of it, and a subagent told to read a missing spec burns its turns on `find /Users/...` before doing anything. Write the files with `write_file` first. Since the folder is ignored, stage explicit paths (`git add app/ test/ ...`), never `.pipeline/`: `git add` of an ignored path fails the whole command.
- **Before re-dispatching, `delegate_task(action='list')` and stop older runs on the same worktree.** A stale engineer left running beside its replacement commits under the same author, and the commits can't be told apart afterwards.
- Batch routine tasks into one dispatch. Risky tasks get their own dispatch and their own review (stage 4) before the next task starts.
- The engineer runs the task's verification command, commits, and appends to the report file: what changed, commands run, raw pass/fail counts.
- **Name-scrub rules need both lists.** When a brief says "never mention X", also list the product's OWN names, domains and hosts that must stay. An engineer told only to avoid other projects' names scrubbed the product's own domain out of the OpenAPI `servers` and README, replacing it with `api.example.com`. A review finding alone didn't undo it: the fix-round engineer kept the scrub, saying it would "violate the session's no-real-domain rule". Restoring it took a brief line marked as an owner-authorized override that names the exact URLs to put back.
- **Proofread the brief against the binding copy rules before dispatch.** Engineers copy a brief's literal examples verbatim even when they break a rule the same brief cites (an example «—» placeholder shipped despite the no-em-dash rule). Every example string in a brief must already be rule-compliant.
- **Give remote access as the exact command** (`ssh -i <key> user@<ip>`), never a host alias from the orchestrator's own ssh config: the engineer's shell doesn't have it, and it silently skips the deploy.
- **An engineer that hits its turn limit or a usage limit** (or dies on a provider error: 402 credits, 429, "request too large"/capacity) leaves committed tasks plus an uncommitted half-task. A usage-limit stop looks like a near-empty run log (`You've hit your session limit · resets <time>`) and NOTHING pushed: check `wc -c run.log`, `git log origin/<b>..HEAD` and `git status` before reporting anything. After the reset (or immediately for a turn limit), dispatch a continuation: the same brief plus a RESUME paragraph naming each local commit and the uncommitted files, telling it to verify the committed items against the brief, finish the rest in plan order, then push. Give big restructures a turn budget of 800+ from the start.
- **Comments describe the code, never its history.** Briefs must forbid review/round tags ("should-fix 5", "fix round 2", "owner decision", finding ids like N3/B2/C1/S10), QA file paths, plan-file references and "used to / now / before the fix / copied from the old X" wording in shipped files; engineers add them by default every round. Make it a `bin/ci` grep gate rather than a review finding: one case-sensitive pass for ids (`(^|[^A-Za-z0-9_])[BCSN][0-9]+([^A-Za-z0-9_]|$)`, `/Users/`, `plan-`) plus a `git grep -niE` pass for phrases (`should-fix|fix round|owner decision|before the fix|used to live`). Don't use `\b` in `git grep -E`: macOS git silently matches nothing with it, so the gate passes while tags ship. Prove every new gate by planting one hit and watching it fail.
- **A regenerated golden/baseline proves nothing.** If an engineer rewrites the "before" fixture mid-refactor (even for a good reason, e.g. it captured a flaky bug), require an independent A/B run: old code (worktree of main) and new code as live servers on the same freshly seeded DB, same request battery, diff status + bodies, classify every difference as planned or bug.

### 4. Architect review

- **No PR is "ready to merge" without an architect verdict on it.** An engineer run that opens its own PR has skipped this stage, and the orchestrator checking the engineer's self-report (checks, files, screenshots, grep) is verification, not review. Start the review the moment the PR exists; report readiness only together with the verdict. Work that already merged unreviewed gets one review of the merged range, focused on what is live now.
- **Other sessions build overlapping features under the owner's account.** On every status check, also grep each open PR you didn't launch for your lane's new class, route and file names (`git diff --stat origin/main...origin/<b>`, `git grep <ClassName> origin/<b>`). On overlap, pause your lane and ask the owner which version stays (one ❗️ question naming both PRs' scope differences). Remove the losing version with `git revert <commit>` on its branch, then read the reverted commit's diff for hunks other commits rely on (a shared route line, a helper) and put those back before running the full suite and pushing. A branch that merged another PR's early commits (an integration branch) carries a stale copy of that PR: clean it up by plain-merging that PR's current branch first, then `origin/main`, and state "merge after #X" in its body.
- **PRs opened by other lanes while you're busy still need their review started.** A feature job that ends by opening a PR notifies no one, and the PR sits with no verdict while you work on another one. On every status check and before ending any turn, run `gh pr list --state open --json number,headRefOid,comments` and start a review for each PR whose last verdict isn't on its current head.
- **A finished fix round goes straight into its re-review in the same turn.** Don't report "ready for another review" and wait: the owner then has to ask for the obvious next step. Fix → re-review → report the verdict is one unit. The only stop is merge or deploy, which needs the owner's go-ahead. This holds when a session was handed only "fix round N" too: a driver whose `status.log` ends at `NO PLAN` (or any early exit) advances nothing, so check `status.log` and the newest `review-N.md` against the PR head before reporting, and if no review covers the head, build `review-pkg-<N+1>.md` from `<last reviewed head>..<new head>` and dispatch the re-review yourself.
- **Re-fetch the base right before pushing a fix round.** The base branch moves while the round runs. `git fetch` + `git merge-base --is-ancestor origin/<base> HEAD` at push time, plain-merge if it moved, re-run the checks on the merge commit, and give the re-reviewer `git diff <fix head> <merge> --stat` so it can confirm the merge touched none of the PR's files.
- Build the review package as a file: `scripts/review-package.sh <base> <head> <out>`. The diff never enters the orchestrator's context.
- **Big PR (~40 files / 2k+ lines): split the review into parallel area reviewers** instead of one reviewer that runs out of turns. Cut one package per area with `git diff <base> <head> -- <paths>` (e.g. screen+sheets / other screens+theme / build+config), one prompt per area from a shared template (area, package path, area-specific focus), each writing its own file with an area verdict. Post ONE comment: first line the overall verdict (Request Changes if any area asks for it), then each area with its first line rewritten to `**Area verdict: …**`, so the verdict grep and the owner see a single verdict. Findings in code that a parallel lane is rewriting (e.g. a component being extracted) go into that lane's engineer brief, not this PR's fix round; say so in the comment.
- **Several requests at once ("do these in parallel, separate PRs"):** one worktree + branch per item, all cut from the same base commit, sharing one dependency install by symlink; each brief names the files the other lanes own. Launch them in one dispatch, and start each PR's review as soon as it exists, in parallel too. When the owner sends several asks without saying "separate PRs", first map each ask to the files it touches: asks that share files (e.g. two changes to the same page's views) go into ONE lane and one PR, since separate lanes would only conflict; independent asks get their own lanes. Bugs spotted while reading for the spec go into that spec as an explicit item, and the launch message lists them and every scope call you made (where a feature applies, what's out) so the owner can redirect before the engineer finishes.
- Dispatch with [templates/review.md](templates/review.md): spec path, plan path, package path, report path.
- Verdict line first: `**Verdict: Approve**` or `**Verdict: Request Changes**`. Findings are `blocker`, `should-fix`, or `nit`, each with file:line and a concrete fix.
- Post the review on the PR as a comment. Self-authored PRs can't take a formal review state.
- **"Send it to Review" with no reviewer on GitHub** (sole collaborator = PR author) means the Hermes kanban board: `kanban_list` for an existing card first, else `kanban_create` one (PR link, branch + head sha, what changed, what's already live, verification counts, open owner decisions, a "Review focus" list of the riskiest points), then `kanban_request_review` on it. The dispatcher spawns the reviewer; findings arrive as a card comment + `changes_requested`.
- **After kanban `changes_requested`, the dispatcher may claim the card for a new implementer run on its own.** If you fix it yourself in the chat session, push, then `kanban_comment` the card at once with the fix commit, how it was verified and "don't re-implement, re-review <sha>": `kanban_request_review` is refused while that run holds the claim, and without the comment two sessions push competing fixes to one branch. Also post the fix summary on the PR.
- "Approved" means the verdict line literally says `Verdict: Approve` on the current head. "The code is ready, only text fixes left" under a Request Changes verdict is not approval: after the fix, get a real Approve verdict, post it, then tell the user. The owner reads the PR and sees every Request Changes comment.
- **Commits that landed after the last verdict need their own review before merge**, even on an old, long-reviewed PR: a merge of main into the branch, or a feature another agent added on request. Read the PR's comment timeline and `git log <last-reviewed-sha>..HEAD`. Put in the review focus: compare every conflicted file with `origin/main`'s version and with what main's recent commits deliberately removed. A "keep both sides" resolution resurrects text main cut on purpose (legal wording, old menu items) and turns it live the moment the feature's env is set.
- **The LAST comment on the PR must be the current verdict.** Profile sessions and parallel runs can post an older round's Request Changes after the newer Approve (seconds apart), and the owner reads the bottom of the thread. Before saying "ready to merge", check `gh api repos/<o>/<r>/issues/<N>/comments --jq '.[-1].body'`; if it isn't an Approve on the current head, run a short final-verdict check on the head (all earlier blockers resolved, gates green, merge method) whose text says which older Request Changes it supersedes, and post it last. Don't explain the ordering to the owner instead of fixing it.

### 5. Fix loop

- Blockers and should-fix enter the loop. Nits go to the ledger as deferred; the final review decides which matter.
- ONE fix dispatch per round with the complete findings list, not one engineer per finding.
- The engineer may push back with technical reasons (see "Receiving review"). The orchestrator rules on each pushback, records `Ruling: <decision> — <why> — <cost if wrong>` in the ledger, and passes it to the re-review.
- Re-review is scoped: [templates/re-review.md](templates/re-review.md) gets only the open findings, the fix diff package (`<previous reviewed head>..<new head>`), and the report. Each finding is ADDRESSED or NOT ADDRESSED. New breakage counts only inside the fix diff. Anything else is an out-of-scope note for the ledger.
- **Owner review comments on the PR** (inline threads he leaves himself) outrank the architect's findings. Fetch them to a file (`gh api repos/<o>/<r>/pulls/<N>/comments --paginate --jq '.[] | "#\(.id) \(.path):\(.line // .original_line)\n\(.body)"'`, plus `issues/<N>/comments` and `pulls/<N>/reviews`), fold them into the same round, and tell the engineer to apply each one across the WHOLE codebase ("check other places" is implied). Post replies in the threads only after the architect has checked every sentence against the code (file:line or commit). Write the replies yourself, not the engineer: engineer drafts were false four rounds running ("already short", "rewrote that spec", wrong line counts, scan totals that didn't add up), each costing a round. Keep each reply to what changed, where, and the commit; leave out counts, "every file" claims and descriptions you haven't checked, and look up each commit with `git log --format=%h main..HEAD -- <file>` instead of trusting a report.
- **Turn style rules into scripted gates, not promises.** "No method over N lines", "no requests inside `it` blocks", "no raw SQL" — an engineer reports "swept every file" and misses a dozen. Have it add a checker to `bin/ci` (method length from the parser's def..end, e.g. Prism; keep RuboCop's `Style/Semicolon` and line-length on so lines can't be joined to cheat) and print a scan of remaining exceptions, each with a one-line rationale. Ask the re-reviewer to script its own count rather than sample.
- **Tests must run with production's privileges.** CI that connects as a DB superuser hides missing GRANTs on a new table, so the feature passes CI and 500s in prod. Require a `bin/ci` step that runs the real queries connected as the app's role, and put "new tables: grants for the app role?" in every review focus that touches migrations.
- **Migration timestamps must sort after the newest migration already applied on prod.** `supabase db push` without `--include-all` refuses local files older than the remote's last applied one, so the deploy job goes red after merge and the new UI runs against the old SQL. When a sibling PR merges a migration first, `git mv` the branch's migrations to later timestamps, update every file-name reference (`git grep <old ts>`, plus QA setup scripts and the PR body), merge main in (plain merge), push, and read the PR's dry-run log: `gh run view <id> --log | grep -A3 'Would push'` must list exactly the branch's files. A green migrate check is stale if it ran before the sibling merged: workflows filtered on `migrations/**` don't re-run for later commits that don't touch them. After the owner merges, confirm `Applying migration <file>` in the main branch's run log before saying it's live.
- **Busy buttons use `aria-disabled` plus an early return, not `disabled`.** Disabling the focused button drops keyboard focus to `body`, and screen readers never hear the busy label. Assert in e2e: focus stays on the button, a second Enter or click sends no request. Interpolated error messages: strip trailing full stops before putting them inside a sentence that ends in one.
- **A reviewer's "acceptable as a known limitation" is a ruling for the orchestrator, not a close.** If the limitation hurts the feature's normal use (e.g. concurrent actions lose their guard and the same paid AI call can run twice), overrule it: post a short orchestrator verdict naming the fix, add a `Ruling:` line, and run it as the next fix round with `resume-pipeline.sh MODE=fix FROM_REVIEW=<that file>`.
- **Cap: 3 rounds.** Still open after round 3 → stop and send the owner the open findings with both sides and a recommendation. Don't adjudicate early to end a loop.
- A "fixed it" commit message is never approval. Only a re-review verdict closes a finding.

### 6. Testing

- Scripts, not model calls: typecheck, unit tests, builds, browser end-to-end suites, real DB checks where data or auth changed. The model reads only pass/fail summaries and failure lines.
- Regression: every existing suite for the touched area, plus a production-like build.
- UI changes: screenshots in the light theme only, desktop and phone, unless the change is about the dark theme itself. One visual check per screen on the final version, not per iteration.
- Screenshots must be full-viewport captures (e.g. 1440x900 desktop, 390x844 phone), never element crops (`locator.screenshot()`, `clip`). A cropped dialog or a 64 px header strip proves nothing: the reader can't see where the element sits, what's around it, or whether it's cut off. Before attaching, check that every element the shot is meant to show is fully inside the frame (bounding box within the viewport, no ellipsis, no clipping).
- Screenshots go only in the PR description, never in comments.
- **Every PR body carries an `## Evidence` section, and the orchestrator checks it before reporting.** Raw suite counts (branch and main), the e2e measurements, and the screenshots uploaded into the body (`gh pr view N --json body --jq .body | grep -c user-attachments` must be > 0 for UI work). Engineers keep shots "local, not uploaded" and reviewers read code, not the body, so a missing section survives two Approves and the owner finds an evidence-free PR. Name the section in the engineer prompt and in the review focus ("Evidence section present with counts and images").
- **Engineers push "evidence" branches and link `raw.githubusercontent.com/...` or `blob/...?raw=true` URLs** in PR bodies. On a private repo these never render (owner sees broken images, twice in one day). Put the rule in `RULES` (upload only via `gh pr edit --attach`, body URLs must be `github.com/user-attachments/...`) and check before reporting: `gh pr view N --json body --jq .body | grep -E 'raw.githubusercontent|blob/.*raw=true'` must print nothing. Repair: `git show <branch>:<file>` the images out, rewrite each URL to `./<file>.png`, `gh pr edit --body-file new.md --attach ./<file>.png ...` in one call (refs get replaced in place, captions kept), delete the evidence branch. Also check the attached images' real pixel sizes (`file -b`): a shot labelled 1440x900 was a 380x1709 element crop.
- `gh pr edit --attach` quirks: outside a checkout pass `-R owner/repo` (it fails with "not a git repository"); attachments get appended at the end of the body in filename order, ignoring `./file.png` references when the body file wasn't built in the same call. Upload, then fetch the published body, map `![alt](https://github.com/user-attachments/...)` URLs by alt name, and rewrite the body with each image under its caption. Refresh `$D/pr-body.md` from the published body afterwards so a running fix engineer edits from the version with the images.
- **Screenshots linked from a side branch don't open.** Engineers sometimes commit shots to an `evidence/<x>` branch and link `github.com/<o>/<r>/blob/<branch>/f.png?raw=true`; in a private repo those render as broken images for readers. Count `user-attachments` in the published body, not just `![`. Repair in one call from the folder holding the PNGs: rewrite each blob URL to `./<name>.png` (`sed -E 's#https://github.com/<o>/<r>/blob/[^)]*/([a-z0-9-]+\.png)\?raw=true#./\1#g'`), then `gh pr edit N --body-file new.md --attach ./a.png --attach ./b.png ...`: references built in the same call are replaced in place under their captions. Then delete the side branch (`git push origin --delete evidence/<x>`).
- Shared test machine: never kill browsers or servers globally (`pkill -f chrome-headless-shell`, `pkill node`, `killall`). Other runs use the same host. Kill only the PIDs you started, or whatever listens on your own assigned ports.
- Keep QA tooling (test scripts, ledgers, review files) in a persistent directory, never in plain `/tmp`: macOS wipes `/tmp` on reboot. For example `~/qa`, with `/tmp/qa` as a symlink. Recreate the symlink after a reboot.
- Worktrees under `/tmp` vanish on reboot too, while their branches stay on the remote. Any shell whose saved cwd was a deleted worktree fails every command (`cd: … No such file or directory`, exit 126), so pass an explicit `workdir`. Run `git worktree prune` before adding a new worktree. Recreate a lost lane from `origin/<branch>` rather than assuming the local commits are gone.
- The architect reviews code, not pixels, so an Approve on a UI PR says nothing about how it looks. Before reporting any UI PR as ready, the orchestrator opens every final screenshot itself (vision) and judges the design, not just presence: raw native radios/checkboxes/selects stacked as a long form inside a polished flow, duplicate control rows, narrow cards beside full-width ones, grey text standing in for a primary button, raw markdown. Fix or route each flaw before reporting; counting `user-attachments` in the body is not a visual check. Download body images with `curl -sL -H "Authorization: token $(gh auth token)" -o f.png <url>` and pass `vision_analyze` the file's path on the terminal host (e.g. `/Users/<user>/...`), not the Hermes-side mount path.
- Vision misreads exact text such as mask lengths, digit counts and long numbers. Check those against the code or a one-line run of the helper before you call them a flaw.
- Never report an alignment or spacing flaw from a vision read alone: vision misjudges centring even on a normal 1440x900 frame (it called a lightbox image "shifted left" that was centred to the pixel). Confirm with numbers first (`getBoundingClientRect` in Playwright, or run-lengths of identical colour along the middle row and column of the PNG with ruby-vips `getpoint` in the project's test image) and compare centres; report the flaw only if the numbers show it, with the numbers. For claims like "no shadow", "text bleeds through", "missing divider", re-ask with `vision_analyze` `region` cropped to that element and yes/no questions, and read the partial's classes: a whole-page critique invents generic flaws.
- When checking a screenshot, also check placement, not just visibility: a dialog must be centred (or anchored to its trigger), not stuck to a viewport corner. "Fully inside the frame" isn't enough; assert the position in tests too.
- Speed-sensitive pages: performance audit before vs after.
- **Responsive proportion and overflow checks for header/logo/nav changes.** A layout that looks balanced on desktop can be off on phones, because breakpoint classes hide lines there (a subtitle hidden below `sm` leaves a 36 px icon next to one 16 px line). Measure with Playwright `getBoundingClientRect` at 320, 360, 390 and 1440: icon height vs text block height, shared vertical centre, and `document.documentElement.scrollWidth <= innerWidth` plus the header row's `scrollWidth <= clientWidth`. Measure production first as the "before", put the numbers in the PR body as a table, and report pre-existing overflow you find as a separate item, not a silent extra fix.
- Local builds without auth env drop signed-out controls (e.g. the sign-in button), which changes header width. Say so next to the screenshot, and for width/overflow work, build with the auth env or reproduce the control.

### 7. Bugs found in testing

- A bug fix is a fix round: the engineer fixes with a failing test first where practical, then a scoped re-review of that diff. Counts against the same 3-round cap.

### 8. Report to the owner

- **Scope status and backlog answers to the system being discussed.** "What haven't we built?" in the middle of work on one service means that service's gaps (data, ops, product, integration, open spec questions), not every repo and old PR the owner has. Answer for the current subject first; mention other projects in one line at most.

Follow [templates/report.md](templates/report.md): PR link, what changed, evidence (exact pass counts, screenshots as attachments), review verdict history, every `Ruling:` line from the ledger, open points, and the next decision needed.

- End with ONE decision phrased so a bare "yes" has one meaning ("Should I do a polish round first?"), not "merge now, or I can polish first?" and not "Should X, or is Y fine?": owners answer a bare "yes" to either-or questions. Put the alternative in a separate sentence after the question if it matters. If the reply is still ambiguous, pick the reversible option, say which one you picked in the first line, and offer to switch.
- **Owner says "merge":** merge each approved PR with `gh pr merge <N> --merge --match-head-commit <approved sha>` (refuses if someone pushed after the verdict). Before merging the next one, run the full suite on a detached `origin/main` worktree with that PR merged in locally: PRs were tested only alone. Report the merge commits and that nothing is deployed yet.
- The owner asks for a preview build to try a PR: deploy the approved head with the flag forced at build time, and verify the flag is inlined before sending the link. "Deploy it" after a merge: production deploy from a clean `origin/main` worktree. Both recipes in [references/preview-deploys.md](references/preview-deploys.md).
- Owner-side prerequisites (env vars, secrets, settings only he can change) go in the report as numbered steps in order, with how you verified their current state (e.g. env var names listed, values never). No deploy or merge without the owner's explicit go-ahead unless the task said so.
- Check what you can of a third-party setup yourself before handing the owner steps, using only public values: e.g. a Supabase project's URL and publishable key are in the live JS bundle, and `GET <url>/auth/v1/health` (version) plus `/auth/v1/settings` (enabled providers) with that `apikey` header tell you whether an upgrade or provider is still missing. Fill the owner's steps with the exact values (callback URLs, origins, provider ids) so he only copies them. Secrets the owner creates (client secrets) go straight into the provider's dashboard; only public ids may come through chat.

## Ledger

`.pipeline/<slug>/ledger.md` in the worktree (git-ignored). First line `# Ledger — <spec path>`. Append one line per event:

```
plan: <path> (approved by owner | auto: routine)
task 3: done <base7>..<head7>, tests 24/24
review 1: Request Changes, 1 blocker, 6 should-fix, 7 nits (comment <url>)
fix round 1: 6 addressed, 1 open (<one-liner>) <a7>..<b7>
Ruling: kept local data on sign-out — user's own device — leaks on shared devices if wrong
deferred nit: <one-liner>
```

After a context compaction, trust the ledger and `git log`, not memory. Never re-dispatch work the ledger marks done.

## Token rules

- The most capable model only for the plan and reviews. A cheaper model for code and fixes. Always set the model explicitly; an omitted model inherits the most expensive one.
- **The owner picks the subagent provider; never route dev subagents through OpenRouter.** When a delegation fails (rate limit, 402, provider resolution), don't switch the provider yourself to whatever is logged in: ask, or use the provider he named (e.g. his Antigravity or Anthropic subscription). The same holds for the detached driver's role CLI: don't rewrite `run_claude` to another CLI or model family because the current one hit a limit; let it wait for the reset or ask. If an earlier turn already swapped it, say so in the next report and name which rounds ran on what. Set it on the Hermes host with `hermes config set delegation.provider <p>` and `delegation.model <m>`, and say in the next message which provider/model the run uses.
- Hand artifacts over as files (spec, plan, brief, diff package, report). Never paste diffs or history into prompts.
- One full review per PR. Per-task reviews only for tasks flagged risky.
- Re-reviews read only the fix diff and the open findings. Small mechanical fix diffs can use a cheaper reviewer.
- Background runs: wait in bounded stretches, check the log tail, don't poll every few seconds.
- Every detached run gets a watcher that notifies the orchestrator when it exits. Finished work must never sit idle waiting to be noticed. For runs that outlive the session (background jobs the session started can be killed when it ends), use a recurring agent cron job (every ~20 min, `continuity: true`, terminal toolset only) that reads `status.log` + process count + `gh pr list --head <branch>`, outputs NOTHING when unchanged (empty output skips delivery), reports new lines in 1-4 lines, and on `DONE`/`NO PLAN`/`NO PR`/`gave up`/dead process says so and asks for the job to be removed. Remove it once the result is reported. Don't set the cron job's `workdir` to a terminal-host path: it's validated on the Hermes host and the create fails; put "always pass workdir=<run dir>" inside the prompt instead.
- **Brand-new product repo for a driver run:** the driver needs `origin/main` to exist. `gh repo create <o>/<r> --private`, clone, commit a README plus `.gitignore` with `.pipeline/` (project author identity), push `main`, then `git worktree add -b feat/<slug> <wt> origin/main`. Tell the architect in `READ_FILES` that the repo is empty and the plan must cover the full scaffold; give the engineer 500 turns. Check the terminal host's toolchain first (runtime version, Docker images already pulled, free disk) and write what the engineer must run in Docker plus a disk floor ("under 3 GB free, stop and report") into the spec's hard limits.
- Fix rounds run only the tests covering the changed code. The full regression set and performance audits run once, right before the report to the owner.

## Receiving review (engineer and orchestrator)

- Verify each finding against the code before changing anything. Restate it, check it, then act or push back.
- Push back with evidence when the finding is wrong for this codebase, breaks existing behaviour, contradicts the owner's decisions, or adds unused features.
- No performative agreement. State the fix and where it is.
- If a finding conflicts with a decision the owner made, stop and ask; don't let the reviewer overrule them.

## Verification before claims

No "done", "passes", or "fixed" without a fresh command run and its output in the same report. Agent self-reports are claims: check the diff, the commits, and the test output before repeating them to the owner.

- An engineer's factual premise ("X doesn't exist on main", "that test file is missing") gets one `git grep origin/main` before you relay it or act on it; they are wrong often enough to derail a brief.
- **Read `gh pr checks <n>` before calling a PR ready**, even with an Approve and a green local suite: a red check the owner sees first costs trust. If it's red, read `gh run view <id> --log-failed` and re-run main's last green run to tell infra breakage (e.g. runner image changed) from the PR's fault. Every job failing in a few seconds with 0 steps means the jobs never started: read `gh api repos/<o>/<r>/check-runs/<job id>/annotations --jq '.[].message'` (e.g. the account's Actions billing or spending limit), run the suite locally, and give the owner the account-side fix as a step instead of touching code.
- **"CI green" is only as strong as the workflow.** Read the workflow file before calling a PR green: if it runs only lint and scans, run the full test suite on the branch AND on `origin/main` yourself and report both counts. Say "lint green, tests not run in CI" otherwise.
- **Claims inherited from an earlier model or session (PR body pass counts, "already drafted", "green") are unverified.** Re-check them, and when one was false, correct it to the owner explicitly in the next report rather than quietly fixing it.
- **A PR written by another agent may be built on a stale copy of shared files.** Before reviewing it, `git diff $(git merge-base HEAD origin/main) HEAD --numstat` and read every deletion in files the feature didn't need; deleted main behaviour (routes, helpers, streaming) usually shows up as calls to methods that exist nowhere. Repair by starting from main's version of each file and re-adding the feature, not by patching the rewrite.
- **Compare test failures with the branch's base, not today's main.** An older branch can fail a check that main fixed after the branch was cut (a brand scan, a copy test), and main can gain failing DB tests once a local test DB happens to be running. Before calling an extra failure a regression, check whether the PR touches the flagged file and run the same file on `git merge-base HEAD origin/main`; report it as "base predates fix X" when that's the cause.
- **Track every lane to a PR, including approved-but-unopened branches and planned-only lanes.** A branch with an Approve but no PR, and a lane whose spec and plan were written but never dispatched because it depended on that branch, both sat forgotten for days while other work ran; the owner had to ask why it wasn't finished. On every status check also list `~/qa/*/.pipeline/spec.md` worktrees with no commits past their base and remote branches with no PR (`gh pr list --state all --head <b>`), and either dispatch them or tell the owner they're parked.
- **A usage-limit stop must never be posted as a review.** A driver once found no verdict and posted the raw "You've hit your session limit" text on the PR as its review. `post_verdict` must refuse a file without a `Verdict:` line (log it, don't post); if one slipped through, delete it (`gh api -X DELETE repos/<o>/<r>/issues/comments/<id>`). `resume-pipeline.sh MODE=review` reruns only the first review on an existing PR whose review died.
- **Background-process completion notices are events to check, not requests.** When the gateway
  reports a driver or test process exited (even with exit -1 and empty output), read its
  `status.log`/log tail and the process list, then tell the owner in one or two lines what it means
  (e.g. "that was the run I stopped; the new one is alive", "it gave up on the usage limit").
  Never answer such a notice with a canned "request not processed", whatever its exit code (0,
  1, -1): the owner then has to ask "try again", and a Request Changes verdict or a stalled run
  sits idle meanwhile. A notice for a run you already replaced gets one line saying so.
- **Run the checks a read-only reviewer couldn't.** Reviews often end with "not run: the tests,
  the mutation check". Before reporting an Approve, run the full suite on the branch and on
  `origin/main`, apply the reviewer's suggested mutation (remove the guard, watch the named tests
  go red, `git checkout -- <file>`, confirm `git status` clean), and redo any real-binary check
  whose recorded output predates the last fix commit. Put the numbers in the report.
- A job that exits with a status update ("still running in the background") hasn't delivered. Check the branch, the PR and running processes yourself, then verify the result like any other.
- An engineer reporting "another agent is running the same task" (a PID doing the same work) is usually looking at its own process or its wrapper: `ps -o pid,ppid,etime,command -p <pid>` before relaying it, and drop it if the PID is gone or is that run's own child.
- **Probe a deployed service yourself before the review, and hand the anomalies to the architect as questions.** Health, auth (no key / bad key / admin without token = 401), a restricted record, a limit overflow (400), rate headers, plus one real query. Anything odd (all distances 0, no next page on a full page, an empty area) goes into the review prompt as `SUSPICIOUS n: <exact request> returned <exact result>; decide data artefact vs bug from the code`. That turned two vague doubts into one confirmed blocker and one documented data gap.

## Pitfalls

- Unattended agent sessions may refuse some tools. Briefs should name the tools the engineer can rely on.
- On a shared host that also runs prod, put in `RULES`: "never restart or stop Docker/Colima, never build ssh tunnels or `/tmp` docker sockets; if docker is unreachable, write it in the report and stop". Engineers otherwise improvise infra workarounds, and a VM restart takes every prod container down with it. Fixing host infra is the orchestrator's job (mac-mini-maintenance).
- `claude -p` engineers sometimes start an e2e script in the background and end the turn "to wait for the completion notification": a non-interactive run then just exits (`NO PR`, near-empty log, local commits). Put "never wait for background notifications; run e2e and browser scripts in the foreground with a timeout" in `RULES`.
- **Chaining a lane after a running driver's stage:** don't wait on `pgrep -f "<stage prompt text>"`. After a turn cap, `run_claude` retries with `claude -c -p "You were stopped mid-task..."` (different text), so the wait ends early and two engineers share one checkout. Wait on the driver's `status.log` line for the next stage (or kill the driver PID AND its subshells first: `pgrep -f "[p]lan-build-review.sh"` lists orphaned `( ... )` subshells too), then confirm 0 `claude` processes with the worktree as cwd before launching.
- Run `bash -n` on every driver/resume copy before launching it. Prompt text lives inside single-quoted `printf` strings, so one apostrophe ("body's") ends the quote; bash only parses the fix loop when it reaches it, so the run dies right after review 1 with `syntax error near unexpected token 'do'`. To fix a copy a run is still executing, overwrite it in place with the same byte length (python `r+b`): `sed -i` swaps the inode and the running bash keeps the old text.
- **A lane that reuses an existing PR** passes the driver's "PR exists" check before the engineer pushed anything, so the review then reads the old `origin/<b>` head and posts a misleading Request Changes. Record the head before launch and, when the engineer ends, compare `origin/<b>` to it: unchanged means resume the engineer (`MODE=engineer`, "push, then rewrite the PR"), not review; delete any review posted on the stale head.
- Resuming a fix round (`MODE=fix`) after a limit stop: pass `PREV_HEAD=<last reviewed head>`. A fix engineer can commit locally before the limit hits; the relaunch only pushes those commits, and without `PREV_HEAD` the loop compares the pushed head with itself, logs `fix N: no new commits`, and skips the re-review.
- Large files get corrupted by read-modify-write through truncated tool output. Edit them with targeted patches only.
- **Scripted insertions: anchor on a string that occurs once.** Python `s.replace(marker, block + marker)` without a count also hits a header comment that names the same section, so a test block lands twice and the pass count is inflated with duplicates. Assert `s.count(marker) == 1` before replacing, and after adding checks run `<test> | grep ^PASS | sort | uniq -d` (must print nothing) before reporting a count.
- Review sessions need a turn budget of 30-40, or they stop mid-read and return nothing useful.
- **Check the raw run log before trusting an extracted verdict.** `sed -n '/Verdict:/,$p' raw > review.md` yields an empty file when the run died early (CLI auth error, usage limit), and a blind `gh pr comment --body-file` would post nothing or stall the loop. `wc -c` both files first. If the CLI itself can't run (e.g. its login expired), run the same role through a `delegate_task` subagent: pass the prompt file path, the worktree, the read-only/edit rules and the exact output file in its context; it produces the same verdict file or pushed commits, and you verify them the same way. Smoke-test the CLI (`claude -p "say ok" --max-turns 1`) before launching a detached driver: an expired login makes every stage exit in seconds with `NO PLAN`. Tell the owner the one-line fix (run `claude` once on that host and log in) and carry on with subagents stage by stage (plan, engineer, review, fix), since a subagent can't run the whole loop unattended. When he says he logged in: smoke-test again, `delegate_task(action='stop')` the stand-in subagent, confirm `git status` is clean and no half-written `.pipeline` file is left, then launch the driver. The stopped subagent's "interrupted" result arrives later; it is expected, just re-check it wrote nothing.
- The reviewer must read surrounding files, not just the diff. Name the key files in the prompt.
- Give the reviewer the PR body as published (`gh pr view N --json body --jq .body > body.md`), not your local draft: after `gh pr edit --attach` the published body has the uploaded image URLs, while the draft still says `./file.png`, and the reviewer flags "screenshots won't render" falsely.
- **The owner merges a PR while its fix round is still running:** run `gh pr view <N> --json state` before dispatching each fix round and again before relaying its result. If merged, steer the engineer at once (before its first push) to carry its edits onto a new branch off the fresh `origin/main` (`git checkout -b fix/<slug>-followups origin/main`; cherry-pick any local commits, no rebase) and open a follow-up PR. If it already pushed to the merged branch (or finished before the steer landed), do the same yourself: cherry-pick its commits onto the new branch, re-run the full suite there, open the PR with each finding and its fix in the body. Pushing to the merged branch reaches nobody. Then tell the owner what in the merged code is wrong until the follow-up lands and which setting keeps it dark (e.g. "don't set the provider's env var yet").
- **Parallel lanes in one repo:** each brief names the files other running lanes own ("don't touch X; keep edits to shared Y additive") and asks the PR body to state its merge order. It keeps conflicts to a few lines instead of a re-review.
- A fix that depends on an approved-but-unmerged PR: branch the new lane from that PR's branch, open it against main, and state the merge order in its body ("includes #X's commit; merge after #X; if #X merges first, merge main into this branch"). Measuring against main instead gives numbers that are wrong the moment the first PR lands.
- Hosting platforms usually won't let a PR author request changes on their own PR. Post verdicts as comments.
- A read-only reviewer still needs permission to write its own output file. Grant edit access to that one path (check how your CLI names file-write rules), or capture stdout and strip everything before the verdict line.
- Claude Code `-p`: neither `Write(<path>)` nor `Edit(<path>)` in `--allowedTools` lets the architect CREATE a new plan file. Tell it to print the plan to stdout starting with a marker line (`# PLAN`) and save everything from the marker on. If a run already ended with "couldn't write", recover instead of re-running: every attempted `Write` call, content included, is in the newest `~/.claude/projects/<cwd with / as ->/*.jsonl`; parse `tool_use` entries named `Write`/`Edit` and write `input.content` to `input.file_path`.
- In driver scripts pass `--allowedTools` as one quoted word (bash array `perm=(--allowedTools "$tools")`, then `"${perm[@]}"`): the read-only list contains `Bash(git log:*)` with a space, and an unquoted `$perm` splits it into broken arguments.
- Guard every background `claude -p "$(cat prompt.md)"` with `test -s prompt.md &&`. If the call that wrote the prompt or diff failed (a wedged or timed-out terminal step), the background job otherwise starts with an empty prompt and you wait on a run that does nothing. Write prompt files with `write_file`, not inside the same shell call that prepares the diff.
- Every brief that creates keys, tokens or passwords must say: pipe the creating command's output straight into a chmod 600 file and never `tail`/`cat` it. An engineer that tails a create-key output to check it leaks the secret into its own log; if it happens, revoke the key and say so in the report.
- A background run reported as "exit -1" with an empty log may still be alive: the notifier lost track, the process didn't die. It also happens when the ssh terminal host itself drops (the check call returns "SSH connection ... timed out"): then say the host is unreachable, that detached runs keep going if only the network dropped, ask the owner to check the machine, and re-check `status.log` and `git log origin/<b>` the moment it answers. Before resuming, check the process tree with a fixed-string match (`pgrep -fF`, or escape regex chars: `pgrep -f "Fix round 3 (LAST)"` silently misses because `( )` are regex groups) and look for fresh commits. A blind resume put two engineers on one checkout. The reverse also happens: the real completion of such a run never gets notified, so on every owner "status?" check `git log origin/<b>` and the run log yourself instead of waiting for a notice.
- **Stopping a driver started with a relative path:** `bash ../resume-pipeline.sh` doesn't match `pkill -f "[q]a/factory/resume-pipeline.sh"`; the driver survives the engineer kill, then reviews the unpushed head and posts a stale Request Changes. Kill drivers by PID (`ps -eo pid,command | grep "[r]esume-pipeline\|[p]lan-build-review"`) and confirm 0 before relaunching.
- **Stopping a remote run by pattern:** `ssh host 'pkill -f <pattern>'` also matches the remote shell running that very command (the pattern is in its own command line), kills it, and ssh returns 255 with no output, so the stop looks failed. Use the bracket trick (`pkill -f "[b]rief-name"`, `ps aux | grep "[b]rief-name"`) and confirm with a separate call.
- **Squash merges carry every commit message by default.** `gh pr merge --squash` writes all
  branch commit subjects and bodies into the squash commit's body, so text a squash was meant to
  keep off `main` (an old brand name, owner name, review tags) lands there anyway. Grep `git log
  origin/main..<branch> --format='%s%n%b'` for the forbidden list first, pass an explicit
  `--subject`, and after merging grep `git log -1 --format='%s%n%b' <merge-sha>` again.
- When the owner says "wait" mid-dispatch, stop the just-launched run at once (kill it, confirm 0 matching processes, check no branch/worktree was created) and say exactly what existed before resuming on his next word.
- Don't ask the engineer to check for other `claude -p` processes itself: it sees its own process tree and stops. The orchestrator checks `ps aux | grep -F "claude -p"` before dispatch and says so in the prompt.
- **Background terminal commands may not run in the `workdir` you passed.** A detached test run
  printed another checkout's `git rev-parse HEAD`, which made a correct run look like it tested the
  wrong commit. Inside background commands use absolute paths (`git -C <wt> ...`, docker `-v <wt>:/app`)
  and record the tested head from the worktree itself, not from the shell's cwd.
- When the terminal runs on a remote host (ssh backend), skill files live on the Hermes host, not
  there: read a script with `skill_view(name, file_path=...)` and write it onto the remote with
  `write_file` before launching it.
- Before and after any local test server, check that its ports are free. A stale server from an earlier build answers instead of the new one, and an agent can spend an hour "fixing" code that works.
- **Review the PR description and body attachments, not only the code diff.** An engineer may collect local test artifacts, measurements, or screenshots without attaching them to the PR (`gh pr edit <N> --body-file ... --attach ...`). An architect must verify that evidence is physically present in the PR description before issuing an Approve verdict on UI, performance, or behavior changes.
